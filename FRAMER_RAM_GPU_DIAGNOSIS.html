Do this first — stops your crashes without touching the site

Your browser has a Framer flag set that no ordinary visitor has

The live page only boots the editor when __framer_force_showing_editorbar_since is present in local storage for this origin. Clearing it should stop the crashes immediately. Do it without loading the page, since loading it is what kills the machine:

  1. Go to chrome://settings/content/all?searchSubpage=smrtsystems.com
  2. Find smrtsystems.com and delete its stored data with the trash icon.
  3. Sign out of framer.com in that browser, or keep Framer work in a separate profile permanently.

This is a workaround for you, not a fix for the site. The site still ships the code path to everyone, and the GPU problem below hits every visitor regardless of this flag.

Two separate problems, two audiences

Orientation

The crashes have two independent causes, and conflating them wastes effort. One is a RAM problem gated behind a flag your browser happens to have. The other is a GPU problem that every visitor pays on every scroll.

Two guards, and neither protects a real user: a === void 0 is a server-side-rendering check, and K is a bot user-agent check.

That bot check is why nobody caught this before launch. Lighthouse, PageSpeed Insights, and essentially every automated auditing tool identify as bots, so they take the early return and never load the editor. The problem is invisible to automated testing by construction. It only shows up in a real browser — which is why it reached production, and why it is your machine that dies rather than a monitoring dashboard.

Three documents are live in the tab simultaneously — the site, the edit shell, and the full editor application. Each carries its own JS heap, its own React tree, and its own listeners. The site’s React runs alongside the editor’s React.

Why this behaves as a leak, not just as bloat

  1. 282 blob: script URLs. The editor fetches the project’s TypeScript and compiles it in the browser, publishing each module as an object URL. A blob passed to createObjectURL() is pinned until revokeObjectURL() is called — garbage collection cannot touch it, because the URL string is itself a live reference. That is a floor of 282 retained modules that never drops.
  2. A live CRDT replica and its websocket. A CRDT retains tombstones for deleted content so replicas can converge, so the structure grows with the project’s edit history and never shrinks. The opening snapshot alone is 1.47 MB, and the socket keeps applying deltas for as long as the tab is open.
  3. It had not finished. Editor requests were still firing at 12.8 s, when Lighthouse stopped recording. Memory was still climbing at the moment measurement ended — the signature of a tab that grows until it is killed, rather than one that settles high.
  4. Garbage collection got 36 ms out of 6.2 s. The heap is not being reclaimed because almost none of it is reclaimable.

Who this actually hits

The escalation is gated on that local-storage key, so a first-time anonymous visitor with a clean browser does not boot the editor. Anyone who has browsed the site while signed into Framer does — which is you, your developer, and anyone else who has touched the project. The staging trace confirms it fired there: 5.9 MB of injected extension JavaScript in the script treemap shows that run used a real signed-in profile, not a clean one.

So the flag is a workaround and the settings toggle is the fix. Priority is unchanged: the people who load this site most often are the people building it.

Fix
  1. Clear the local-storage flag on every machine that has browsed the site while signed into Framer — see the box at the top. This is what stops the crashes today.
  2. Turn off On-Page Editing for the published site in Framer’s site settings. This removes the code path for everyone, and is the actual fix.
  3. If the toggle does not exist on the current plan, escalate to Framer support with the two excerpts above. A published site compiling 338 source modules and loading a 1.47 MB collaborative document in a visitor’s browser is not intended behavior.
  4. Meanwhile, use separate browser profiles for building and for viewing, so an editor session is never attached to a normal page load.

The file is not big because it is high-resolution. It is big because it is over-encoded and 29 seconds long. A 720p background loop wants 6–10 seconds at 1–1.5 Mbps, which is where the “under 1.5 MB” target comes from. This matters for the GPU question specifically: at 720p, a decoded RGBA frame is only 3.5 MB, so all three elements together account for roughly 28 MB of texture. Real, but not what is saturating your GPU — see the next section.

The 28.90 MB file is loaded by two elements, because desktop and mobile breakpoint variants are both in the DOM. The staging trace shows the consequence: six range requests for one file, one of them pulling 23.94 MB.

Neither file is fast-start optimized. The moov metadata atom is absent from the first 3 MB of both files — it sits at the end. A player cannot begin until it has fetched the tail, which is exactly why the waterfall shows a small request, then a seek, then a bulk transfer. Re-muxing fixes this at zero quality cost.

All three carry loop, so decode buffers are never released. And preload="none" with no poster means the hero paints nothing until buffering starts — a large share of the 3.1 s LCP.

Fix
  1. Re-encode. Keep 720p; cut to 6–10 s; H.264 at CRF 28–30; confirm no audio track; add a VP9/WebM alternate. Target under 1.5 MB, down from 28.90 MB.
  2. Re-mux with -movflags +faststart so playback can begin without fetching the tail.
  3. One video element, not one per breakpoint.
  4. Add a poster — first frame as compressed WebP. Fixes the empty hero and the LCP together.
  5. Pause off-screen with an IntersectionObserver.

The GPU load — it isn’t the video

4 findings

You asked me to check image and video scaling, on the theory that oversized media is saturating the GPU. Media scaling is wrong here, and finding G4 covers it. But it is not what is loading your GPU. The videos are 720p and 540p; their decoded frames total roughly 28 MB, which does not trouble a modern GPU.

This is what does.

G1 P0 Compositing Confirmed live

252 elements animate a blur filter, and every one of them is a separate offscreen render pass

All 252 standalone filter: blur() declarations on the live homepage are inline styles, and all 252 share one signature.

The inline style, identical across all 252 occurrences 
display:inline-block;
opacity:N;
filter:blur(Npx);
transform:translateX(Npx) translateY(Npx) scale(N) rotate(Ndeg) skewX(Ndeg) skewY(Ndeg)

display:inline-block plus a per-element transform plus a blur is the signature of a per-character or per-word text reveal with the blur appear-effect enabled. The page carries 1,074 framer-text spans; 252 of them are animating a blur.

The reason this is expensive is how blur must be implemented. A CSS blur cannot be composited in place. The element is rendered to an offscreen render target, convolved in two passes — horizontal, then vertical — then composited back. That is three GPU passes and one extra full-size texture allocation per element, per frame. With 252 of them animating together during a scroll reveal, the GPU is doing on the order of 750 render passes per frame, each with its own texture.

Every one of those elements also carries a transform, which promotes it to its own compositor layer. Layers are not free: each holds a texture sized to its painted area.

Fix
  1. Turn off the blur component of the text appear effect, keeping the fade and the slide. This removes roughly 750 render passes per animated frame and is the single largest GPU win available. Visually it is a subtle change; measurably it is not.
  2. Animate whole headings rather than per character. That takes 252 animated layers down to about a dozen — and independently fixes the screen-reader problem the pre-launch audit raised about split text being read one character at a time.
G2 P1 Compositing Confirmed live

32 backdrop-filter: blur(14px), the most expensive operation in CSS compositing

Separate from G1, and individually worse. Unlike filter, backdrop-filter must sample what is already painted behind the element, so the compositor has to resolve and read back the backdrop, blur it, then re-composite. It defeats most of the compositor’s caching. Thirty-two on one page is extreme.

Fix

For frosted panels sitting over a static background, a semi-transparent solid fill is visually near-identical and costs nothing. Reserve backdrop-filter for the one or two places it genuinely needs to read as glass.

G3 P1 Why it’s your PC Mechanism

Windows display scaling multiplies every one of those textures

Compositor layer textures are allocated in device pixels, not CSS pixels, so their memory scales with the square of the device pixel ratio. At Windows display scaling of 150%, every one of those 252 blur render targets is 2.25× larger. On a 4K panel at 200%, 4× larger.

That is the difference between a page that feels sluggish on a 1080p monitor and one that exhausts GPU memory on a scaled 4K one. It is also why this reproduces on your machine and may not on someone else’s, with identical browsers.

Three defects, in order of cost:

  1. srcset offers exactly one width per image. The sizes attribute is elaborate — (min-width: 1200px) max(max((100vw - 192px) / 3, 1px), 100vw), … — and entirely inert, because there is only one candidate to choose between. A phone downloads and decodes the identical 1086 × 1448 asset a desktop does.
  2. They are PNG. A 1.57 MP product screenshot as PNG is far heavier than the same image as WebP or AVIF. Lighthouse independently scores 351 KiB of savings on image delivery.
  3. They are oversampled against their display size. The sizes value implies a three-column layout — roughly a 360 px column at a 1200 px viewport — so a 1086 px-wide asset is about 3× wider than it is ever displayed. Decode and texture upload happen at intrinsic size regardless of the CSS box, so that waste is paid in full.
Fix

Give the images real srcset variants at 400 / 800 / 1200 px and serve WebP. Framer generates these automatically when an image is placed as a responsive image rather than a fixed asset — worth finding out why it did not here, since the elaborate-but-useless sizes attribute suggests the intent was there.

G5 P1 Layer promotion Confirmed live

31 permanent will-change declarations

transform on 24 elements, transform, opacity on 3, width on 3, plus 4 set to unset. will-change is meant to be applied immediately before an animation and removed afterwards. Left on permanently, it pins a compositor layer and its texture for the entire life of the page — which is the opposite of the optimization it looks like.

Confirm all of this yourself in two minutes

In Chrome DevTools on the live site, before and after disabling the blur effect:

  • Rendering panel → enable Layer borders. Every border is a compositor layer; expect a great many over the animated headings.
  • Layers panel → sort by memory. This gives the actual per-layer texture cost and names the worst offenders directly.
  • Performance panel → record a scroll through the hero. Look for tall Composite Layers and Paint bands, and check the GPU track.
  • chrome://gpu → watch the process memory figure while scrolling.

That comparison is the cheapest way to prove where the load actually is, and it will give you real numbers where mine are arithmetic.

R1 Reference WebGL Not on live homepage

Retained for reference: a WebGL layer that was in the staging build only

None of this appears in the live homepage HTML — zero references. It was in the staging build. Retained here in case it exists on other pages, and because it is the kind of thing that comes back.

These two libraries trigger forced synchronous reflow from seven distinct call sites. But WebGL is the memory concern: a context allocates GPU-side textures and framebuffers that never appear in JS heap measurements. A blue_noise texture indicates a shader-based dithered gradient running continuously.

The specific risk is remounting. If the effect’s container re-renders — on a breakpoint change, a route transition, a scroll trigger — and the old context is not released via loseContext(), contexts accumulate. Browsers cap concurrent contexts around sixteen and then start discarding the oldest, which produces exactly the “looks fine, then goes black or dies” behavior.

That controls.umd.js is present at all is its own tell: it is the library’s authoring control panel, 71% unused, and has no business on a published page.

Fix
  1. Remove controls.umd.js — it is editor UI, not runtime.
  2. Verify teardown: resize across the mobile breakpoint several times, then check the WebGL context count. If it climbs, the component needs an unmount handler calling loseContext().
  3. Deduplicate — all three assets load twice, again from breakpoint duplication.
  4. Gate it behind prefers-reduced-motion, and consider skipping it on mobile entirely, where the RAM ceiling is lowest and the effect least visible.
  5. Weigh it honestly: 630 KB, a permanent GPU allocation, and seven forced reflows for a decorative gradient. A static WebP costs nothing.

C2 P1 Main thread Confirmed

Framer Motion is the largest single main-thread cost, at 3,002 ms

motion.C_WWXFrT.mjs alone accounts for 3,002 ms — more than the entire document’s 1,425 ms — and appears twice in the forced-reflow table.

The likely amplifier is finding 19 of the pre-launch audit: heading text split into per-character spans for reveal animations. Every character becomes an animated node with its own transform and style recalculation. Across several headings, doubled for two breakpoints, that is thousands of animated nodes. It explains the 853 ms of style and layout, and it is a steady allocation load rather than a one-time cost.

Fix
  1. Animate whole headings, not characters. A single opacity and transform on the heading gets most of the effect for a fraction of the cost — and it fixes the accessibility problem the pre-launch audit raised about screen readers reading split text one character at a time.
  2. Animate only transform and opacity, which stay on the compositor and skip layout entirely.
  3. Unmount reveal animations once they have played. A one-shot intro should not stay mounted and observed for the life of the page.
  4. Honor prefers-reduced-motion.

Consolidating the header, hero, footer, and testimonial marquee into single responsive components is the highest-leverage structural change available, because it reduces four independent problems at once.

Fix order

Grouped by symptom

Steps 1 and 2 address the RAM crashes; 3 through 6 address the GPU load you saw in Task Manager; the rest is payload that every visitor pays. Step 1 is the only one that helps you in the next five minutes.

  1. Clear the local-storage flag on affected machines. Stops your crashes today, changes nothing for anyone else.
  2. Disable On-Page Editing in Framer site settings. Removes the editor code path for everyone — the actual fix for the RAM problem.
  3. Disable the blur on the text appear effect. Removes roughly 750 GPU render passes per animated frame. Largest single GPU win.
  4. Animate whole headings, not per character. 252 animated layers down to about a dozen, and it fixes the split-text screen-reader problem at the same time.
  5. Cut the 32 backdrop-filter blurs to the one or two that genuinely need to read as glass.
  6. Fix image delivery — real srcset variants at 400/800/1200 px, WebP instead of PNG.
  7. Re-encode both videos — 38.6 MB to under 3 MB, and re-mux with +faststart.
  8. Consolidate the hero to one video element, then the header, footer, and marquee.
  9. Cut the font set to the families and weights actually used; move to variable fonts.
  10. Decide on the frameship licence script; add lang="en" to the document root.

Expected result: visitor payload from roughly 30 MB to 3–4 MB; requests from 1,090 to under 120; main-thread work from 6.2 s toward 2 s; GPU compositing from 252 animated blur layers to about a dozen plain ones; and a heap that settles instead of climbing.
