Why PageSpeed Insights times out

Not a separate bug

RPC::DEADLINE_EXCEEDED: context deadline exceeded is not a fault in PSI and not something to chase separately. PSI runs Lighthouse on Google’s infrastructure under a hard backend deadline. This page ships a 17 MB video, spends 10.5 s of main-thread time on mobile, and produces 20 long tasks. It never reaches a stable state inside the deadline, so the RPC is killed.

Your local runs succeed because a local Lighthouse has no server-side deadline — it waits as long as the page needs. The timeout is a symptom of the same payload problem and will resolve itself once the video is fixed. It is also a useful canary: when PSI starts completing again, the page has genuinely improved.

The resolution is fine. The bitrate is absurd. 28.90 MB for 29.3 seconds of silent 720p is about 7.9 Mbps — roughly eight times what that resolution needs. The file is big because it is over-encoded and 29 seconds long, not because it is high-resolution.

Neither file is fast-start optimized. The moov metadata atom sits at the end, so a player cannot begin until it has fetched the tail. That is why the waterfall shows a small request, then a seek, then a bulk transfer.

And it is not only bandwidth: the video is the second-largest layout-shift contributor on desktop, at 0.255 of 0.817, because with no poster and no reserved aspect-ratio box the layout reflows when it finally paints.

Fix
  1. Re-encode: keep 720p, cut to 6–10 s, H.264 at CRF 28–30, confirm no audio track, add a VP9/WebM alternate. Target under 1.5 MB, from 28.90 MB.
  2. Re-mux with -movflags +faststart so playback starts without fetching the tail.
  3. Add a poster and an explicit aspect ratio. This is a CLS fix as much as a perceived-speed fix.
  4. One video element, not one per breakpoint.
  5. Pause off-screen with an IntersectionObserver.

Fixing this single asset takes the page from ~19 MB to ~2.5 MB and should move desktop performance from 24 into the 60s on its own.

Late-arriving web fonts reflow the page, and one of them belongs to the WebGL library

Mobile CLS is fine at 0.045. Desktop is 0.817 — eight times the failure threshold.

Named culprits — all late fonts 
fonts.gstatic.com   …v6/or3yQ6H-1….woff2          430 ms est savings
fonts.gstatic.com   …v5/gyBjhwUxI….woff2          340 ms est savings
unicorn.studio      …google_fonts/JTUSjIg69….ttf    70 ms est savings

Text renders in a fallback face, the real face arrives, and everything reflows. Lighthouse scores 430 ms of savings on font-display alone. Note the third line: the WebGL library ships its own Google font, and it is measurably degrading a Core Web Vital.

Fix
  1. Set font-display: swap and add font metric overrides (size-adjust, ascent-override) so the fallback occupies the same space as the real face. Metric overrides are what actually kills font-driven CLS — swap alone just makes the shift visible instead of invisible.
  2. Give the video and div.framer-37j7oc explicit dimensions or aspect-ratio, so their boxes are reserved before content arrives.
  3. Cut the font set. Fewer faces, fewer opportunities to shift.
  4. Remove unicorn.studio and its bundled font goes with it.

Three things make this poor value:

P1-2 P1 GPU Confirmed live

252 elements animate a blur filter — roughly 750 GPU render passes per frame

The inline style, identical across all 252 occurrences 
display:inline-block; opacity:N; filter:blur(Npx);
transform:translateX(Npx) translateY(Npx) scale(N) rotate(Ndeg) skewX(Ndeg) skewY(Ndeg)

That signature — inline-block plus a per-element transform plus a blur — is the per-character text reveal with the blur appear-effect enabled. There are also 31 permanent will-change declarations.

A CSS blur cannot composite in place. The element renders to an offscreen target, is convolved in two passes, then composites back: three GPU passes and an extra full-size texture per element, per frame. Layer textures are allocated in device pixels, so Windows display scaling at 150% multiplies every one by 2.25×, and 200% on a 4K panel by 4×. That is why this bites your machine specifically.

This is also very likely a large share of the 3,940 ms mobile TBT and 10.5 s mobile main-thread time.

Fix
  1. Turn off the blur component of the text appear effect, keeping the fade and slide. Largest GPU win available.
  2. Animate whole headings rather than per character — 252 animated layers down to about a dozen, and it fixes the screen-reader problem with split text at the same time.
  3. Cut backdrop-filter to the one or two places that genuinely need glass.
  4. Audit will-change so it is applied before an animation and removed after, not left on permanently.

Confirm in DevTools → Layers sorted by memory, and Rendering → Layer borders, before and after.

  • /blog/{slug} → /blogs/{slug} — the new site pluralised the path. If the old site used /blog/, all 34 posts are currently 404ing for Google. This is the single most likely and most valuable redirect set.
  • /contact → /contact-us

I could not enumerate the actual old URLs — this environment’s egress policy blocks web.archive.org. You can get the real list in ten minutes, and you should before building the map.

How to build the map properly
  1. Search Console → Indexing → Pages, plus Performance → Pages filtered to the 16 months before cutover. That is the authoritative list of what Google had indexed and what was actually earning clicks.
  2. Sort by impressions and redirect the top pages first. A long tail of zero-traffic URLs can 404 without consequence; the top 20 cannot.
  3. Point each old URL at its nearest relevant page, not the homepage. Blanket homepage redirects get treated as soft 404s and pass nothing.
  4. Resubmit the sitemap, then watch Coverage for a 404 spike — that spike is your remaining redirect to-do list, arriving for free.
  5. Add <lastmod> so Google has a recrawl signal. Framer should populate it from CMS timestamps.
  6. Request indexing for the homepage and the seven /tech/* pages to prime the crawl.
  7. Two blog slugs still carry stale years — seo-in-2025-… and decoding-local-seo-…-in-2024. Decide now, since reslugging later means more redirects.
